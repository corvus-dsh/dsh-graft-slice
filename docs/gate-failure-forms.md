# 本地绿 / CI 红：三道实物证据（AUD-16 的落地）

> B4-0b-2 W1-12。判据原文：**「本地全绿 ≠ CI 全绿」不是一句提醒，而是一种有具体形状的缺陷** ——
> 这三道都是同一个动作：**本地那道检查回答的是 A 问题，CI 红的是 B 问题。**
> 收口时不需要再加一道闸门（三道都已有对应判据），需要的是**记住它们长什么样**。

---

## ① 改了 `src/`，没重新提交构建产物

| 项 | 值 |
|---|---|
| 仓 | `dsh-paradise` |
| 症状 | 本地 `npm test` 全绿；CI `Gates` job 红 |
| 真因 | `dist/harness.js` 是**提交进仓的构建产物**，`src/` 改完后没重建 ⇒ 仓里的产物与源码不一致 |
| 本地为什么看不见 | 测试 import 的是 `index.js`；**没有任何本地检查把「仓里的 dist/」与「重新构建的结果」比过一次**。而 `index.js` 从第一天就有这道检查 —— 缺口不是「没有新鲜度检查」，是「检查只覆盖了两个产物中的一个」 |
| 修法 | `scripts/preflight.mjs` 增加 4b：把 `composeHarness(root).output` 与 `dist/harness.js` **逐字节**比较 |
| 判据 | `node scripts/preflight.mjs` 在「只改 src、不重建 dist」时必须 FAIL；`npm run check` 已含 preflight |
| 形态名 | **检查覆盖了同类对象的一部分**（一个产物有、另一个没有） |

配套的构建侧改动：`scripts/build-harness.mjs` 把组合逻辑抽成 `composeHarness(repoRoot)` 并导出，
`root` 从 `import.meta.url` 派生改为**参数** —— 否则导入方会用本文件的位置去组合别人的树。
写入磁盘只在 `isMain` 时发生，这样 preflight 能「比较而不写」。

## ② 测试里手写路径分隔符（`${plain}\`）

| 项 | 值 |
|---|---|
| 仓 | `dsh-graft-slice`，测试 `v257` |
| 症状 | 本机全绿；CI `Test` job 红（22.x / 24.x 都红） |
| 真因 | `${plain}\` 在 Windows 上是「同目录下的兄弟」；**在 POSIX 上 `\` 是合法的文件名字符**，于是 `resolve()` 给出两个不同的字符串 |
| 本地为什么看不见 | 这个差异**只能由另一个 OS 暴露**。Windows 上任何本地运行都不可能失败 |
| 修法（当场） | 删掉那处拼写，改用 `path.join` |
| 修法（复发防护） | `scripts/check-test-separators.mjs`：检出「值 + 裸反斜杠」的三种形态，接进 `npm run check` **和** ci.yml |
| 判据 | 自测 6 例（`\n` / Windows 字面量 / 正则转义 / `path.join` 全不误报）；注入 v257 原形态 ⇒ 点名文件与行号 |
| 形态名 | **本地的判定维度里没有那个差异** |

这道检查自己走了两稿才写对，值得记：

1. 第一版「反斜杠跟在插值后面」⇒ **37 行误报**，全是断言消息里的 `\n`；
2. 第二版用 lookahead 排转义，位置写反了 ⇒ **787 行误报**，更糟；
3. 正确说法：**反斜杠后面跟着字母/数字/反斜杠 ⇒ 是转义；否则才是分隔符。**

一个会把 `\n` 报成路径分隔符的检查器，一周内就会被关掉。

## ③ 计数漂移（README 写 381，实测 384）

| 项 | 值 |
|---|---|
| 仓 | `dsh-paradise` |
| 症状 | 本地全绿；CI `Gates` job 红 |
| 真因 | `security-known-limit` 从 3 条扩到 6 条，README 的数字没同步（381 → 384） |
| 本地为什么看不见 | 计数断言跑在 CI 的 Gates 步骤里；本地 `npm test` 不跑文档一致性 |
| 修法 | 同步数字；长期由 W4-1 的「计数复用真实测试输出」覆盖 |
| 判据 | `check-readme-counts` 与 `check-docs` 都在 `npm run check` 链上 |
| 形态名 | **同一个事实有两个来源，且只有一处会被更新** |

## 三条并列的结论（§九「判据分裂」的经验补充）

这三道和应用层的三条「看不见」是**同一个动作**，只是层次不同：

| 层 | 形态 | 本例 |
|---|---|---|
| 检查的**对象**覆盖不全 | 同类对象只查了一部分 | ① dist 没查、index.js 查了 |
| 检查的**维度**看不见差异 | 比较发生在一个不含该差异的量上 | ② Windows 的判定里没有 POSIX 语义 |
| 检查的**来源**只有一处更新 | 一个事实两个来源 | ③ README 数字 vs 实测 |

对应的应用层三条（本批踩到的）：

- 断言写成被审对象的语法（`v270 ②`：`/^aliases:\s*tags:/mu`，`\s` 匹配换行 ⇒ 会匹配合法输出）；
- 检查只看文件里的子串（frontmatter 门禁第二版，**被注释满足**）；
- 基线只记文本是否存在（第三版，**看不见次数**）。

**共同的一句话**：比较发生在一个看不见该差异的维度上，于是它永远通过。
验收报告里这三条与上面三道并列写，因为它们要防的是同一种读者反应 ——
「有人查过了」。

## 操作注记（不是判据，但会复发）

1. **提交信息一律 `git commit -F <file>`，文件由 `edit`/`write` 写**。
   `Set-Content` / `Out-File -Encoding utf8` 会写 BOM（`EF BB BF`），在 `git log --oneline` 里表现为
   subject 首字符异常。实测 `--format=%B` 读出来是干净的（PowerShell 解码流时吞掉流首 BOM），
   仓库内唯一的提交信息读者 `verify-bundle.mjs` 用 `\[export-change\]` 子串搜索，不受影响 ——
   但 BOM 对以后可能引入的 changelog / subject 解析器有风险。
2. **`git add -A` 必须在 `verify-bundle` 改写 `.export-surface.json` 之后**。
   反过来的顺序会让基线文件留在工作树外，`v238 ④` 变红（实测踩过一次）。

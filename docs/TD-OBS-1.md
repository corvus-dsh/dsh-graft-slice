# TD-OBS-1 · 观测路径与直接执行的判定曾不一致（环境条件，非工具缺陷）

> 登记依据：lead §三十九.4 —— 允许红树提交的第四个条件「该红已登记为带编号的待修条目」。
> 状态：**已定性，未修**（定性结论：不可复现于干净树）。

## 一、报告的现象（dsh，2026-11-24）

同一个工作树，三个数字：

```
node --test test/*.test.mjs                      → 1122 pass / 0 fail
node --test --test-reporter=tap test/*.test.mjs  → 1122 pass / 0 fail
node scripts/check-readme-counts.mjs（观测路径）  → 64 fail（缓存未清时 23 fail）
```

失败名集中在**会派生子进程**的测试：`v238` export-surface / 「环境变量仍然优先于 git log」/ `v0.9.5`。

## 二、lead 的独立复核（同一时段，全部为绿）

| 路径 | lead 实测 |
|---|---|
| A 直接跑 | 1122 / 0 |
| B `check-readme-counts`（清缓存后） | **exit 0**，连跑 3 次 |
| C TAP 直接跑 | 1122 / 0 |
| 两条路径的 TAP 计数对照 | **逐项相同** |

## 三、dsh 在干净树上的复核（2026-11-24 修复后）

```
git status --porcelain → 空（干净树）
node scripts/check-readme-counts.mjs → EXIT=0
```

**⇒ 不可复现。** 三个数字全部收敛到「绿」。

## 四、排除掉的假设

| 假设 | 检验 | 结果 |
|---|---|---|
| `NODE_TEST_CONTEXT` / `NODE_TEST_WORKER_ID` 存在导致分支不同 | `node -e` 打印两者 | 双侧均为 `undefined`，`delete` 是空操作 ⇒ **排除** |
| 观测命令与直接命令不同 | `probe-observation-parity.mjs` D3 | 两条路径 TAP 计数**逐项相同** ⇒ **排除** |
| 缓存陈旧 | 清缓存后重跑 | 清后仍报 64 ⇒ **不是缓存**（但缓存曾把 23 遮成一次旧读数） |
| `env` 未传给子进程（死代码） | 读 `suite-observation.mjs:274` | `env` **确实传了** ⇒ **排除** |

## 五、最可能的解释（**未证实**，写清是假设）

报 23 / 64 的两轮，dsh **正在同时修改** `scripts/*.mjs`、`test/*.test.mjs` 与四仓同步。
`v238` 的 export-surface 判据会读**工作树状态**（`git status` / HEAD 差异），而 `v0.9.5` 同类。
在**脏工作树**下，这类判据本来就会红——**那不是观测路径错了，是它如实报告了脏树。**

`check-readme-counts` 的语义是「测试套件不全绿就不判文档」——它在脏树上红是**正确行为**。

## 六、给下一次的判据（未实现）

要让它成为**确定性**判据（而不是「有时红有时绿」），需要：

1. `check-readme-counts` 在报「套件未全绿」时**同时打印 `git status --porcelain` 的行数**，
   让读者一眼看出「红是因为树脏」还是「红是因为代码坏」；
2. 若脏树且失败的测试名全部属于「读工作树」的那一类 ⇒ 结论写 **DIRTY-TREE**，不写「套件未全绿」。

**未实现。** 这是把「环境条件」与「产品缺陷」分开的那一步，与 `registry 404` 那次同族。

## 2. bench-smoke：本仓的纯函数微基准

被测函数：`parseIdentityMetadata`（`src/core/host-shape.ts`，sha256 `179e74d219bd`）

命令：`node scripts/bench-smoke.mjs`
规模：100 000 次调用 × 7 轮，报**每轮 per-call 耗时的中位数**。

| 轮次 | 三次独立运行的中位数（ms/call） |
|---|---|
| run 1 | 4.005e-4 |
| run 2 | 3.976e-4 |
| run 3 | 3.859e-4 |

- **中位数：3.98e-4 ms/call**（约 0.40 µs）
- 三次运行极差 / 最小值 = **1.04×**
- can-red 自检：空实现中位数 3.4e-6 ms，**分离度 121×**，SIGNAL-OK

选它的理由：每次调用都要构造 RegExp、匹配、`JSON.parse` 一个对象、逐字段做类型判定 ——
工作量足够让量具分辨「做了事」与「没做事」。它经 `index.js` 导出（既有形状）。

**第一版候选是 `utils/serialize.ts` 的 `truncateEnd`，被 can-red 自检否掉**：
实测 separation=1.57× / spread=673%，落在 NO-SIGNAL 区。原因不是它坏了，
是它**太快**（约 6e-6 ms/call，与空调用同量级），量具测到的主要是循环与调用开销。
这种基线对未来的回归完全无知 —— 函数体慢 10 倍，输出也只动一点点。

> 注：`host-shape.ts` 不能直接从 `src` 加载（它内部 `import './constraint-shape.js'`，
> Node 的 type stripping 不把 `.js` 重写成 `.ts`），所以走构建产物 `index.js`。

## 3. 为什么**不设阈值**

**先有基线，才有阈值。** S2 性能基线（2026-11-09）的教训：50 并发 p95 = 7.26ms 里
**76.6% 是排队**，不是计算。用「并发 p95」当分母，会把排队时间当成自己的预算，
把可见的计算增长说成"可忽略"。

所以 B0 只记基线：**基线是事实，阈值是判断**。判断需要知道正常波动范围，
而那个范围现在还不知道 —— 本仓 1.04× 的极差说明这台机器上够稳，
但**不足以**支撑「超过 X% 就报警」这种判断（换机器、换 Node 版本、CPU 降频都会改变它）。

## 4. bench-smoke 自带 can-red

脚本内部跑两次：一次真函数、一次空实现 `() => {}`，并断言**真函数的中位数必须显著更高**
（当前门槛 2×）。不满足就打印 `NO-SIGNAL`，而不是装作测到了。

这条自检在本仓**真的否掉了一个候选**（`truncateEnd`，见上）。
没有它，这里会写着一个 6e-6 ms 的漂亮数字，而那个数字测的是循环开销，不是函数。

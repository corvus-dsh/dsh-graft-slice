## 一、为什么需要这份文件

`v2.3` §15.18.4 写着一条纪律：**指标不得事后倒改**。而我（lead）在 §28.7 写的「连续 3 代」是
**自己造的数**，而且**是在结果出来之后定的** —— 那正是这条纪律要防的事。

所以「稳」的定义必须**先写死、后观察**，并且**可验证它没被改过**。

## 二、窗口：L0 下限 **2 小时**（不是我造的「3 代」）

来源：`v2.3` §15.18.3 的阶梯，L0 = **2–6 小时**。取**下限 2 小时**作为「稳」的最低门槛。

### 2.1 工作负载定义（**这是本文件的核心**）

`v2.3` §15.18.2 明写：**「仅保持进程存活、发空心跳不构成证据」**。
所以 2 小时的窗口内，下列六类活动**各至少发生 1 次**，否则该次观察**不计入**：

| # | 活动 | 可观测的判据 |
|---|---|---|
| 1 | **目标推进** | 任务图某个节点从 `pending`/`active` 走到 `done`（`memory_graph_update` 的变更记录） |
| 2 | **工具执行** | 至少一次真实工具调用产生了副作用（写文件 / 跑测试 / 提交），不是只读 |
| 3 | **结果检查** | 对上一步的结果做了核对（读回、跑门禁、比对哈希） |
| 4 | **错误处理** | 至少一次失败被识别并处置（修复后复跑，或记录为未修） |
| 5 | **记忆检索** | 至少一次 `memory_search` / `knowledge_query` 命中或明确未命中 |
| 6 | **阶段验收** | 至少一个阶段的出口条件被逐条核对（不是「跑绿了就算」） |

**六类缺任何一类 ⇒ 该窗口作废，重新计时。** 这一条我事先写下来，是为了防止「跑了两小时空转也算稳」。

## 三、对象：**逻辑会话**（`generationId` 链），不是进程

一次观察的对象是**一条代际链**（从某个 `generationId` 起到它被切片为止），不是「一个 node 进程」。
理由：进程可以重启，代际链才承载「上下文是否被正确交接」这件事。

## 四、判据：**出现 1 次「压缩早于预警」即判不稳**

### 4.1 代价论据（**事先就能写的**，不是事后合理化）

> **压缩吃掉的是不可重建的上下文；误降级的代价是可恢复的（用户可把 `auto` 置回 `true`）。**
> **两条代价不对称**，所以判据必须不对称：一次失败就够判不稳。

这不同于「连续 3 代无失败才算稳」——那是把**样本量**当成了**证据强度**。在不对称代价下，
正确的做法是**一次即判**，而不是等统计显著。

### 4.2 触发后的动作

1. 按用户授权把该 profile 的 `auto` 置 `false`（**阈值型压缩**被关掉）；
2. 审计与面板写明「按用户授权的降级」，**长期显示**（不是弹一次）；
3. **只有用户能置回 `true`**，且**恢复也必须被记录**（否则下次事故查不出「它什么时候被打开的」）；
4. **不许振荡**：降级后在同一 profile 内保持，**不因「连续 N 代没再观测到」自动恢复**——
   自动恢复等于把闸又交给同一条刚刚错过一次的判据。

### 4.3 溢出型压缩**不触发**降级

`auto:false` 关的是**按阈值自动压缩**，**关不掉 API 溢出后的强制压缩**。
所以溢出型压缩单独记 `overflow-compaction-observed` 并**升级上报**，**不许用它触发降级** ——
那只会关掉一个有用的东西，而挡不住它本来要挡的那件事。
